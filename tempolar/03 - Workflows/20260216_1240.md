# 🎯 اصلاً هدف این تمرین چی بود؟

این تمرین سه تا چیز خیلی مهم رو می‌خواست تو مغزت جا بندازه:

---

## 🧠 1️⃣ جدا کردن Logic از I/O

تو یاد گرفتی:

- Workflow → فقط orchestration و تصمیم‌گیری
    
- Activity → جایی که I/O اتفاق می‌افته (HTTP, DB, API, etc)
    

❌ Workflow نباید HTTP call بزنه  
✅ Activity باید این کار رو بکنه

چرا؟

چون Workflow باید **Deterministic** باشه.

---

## 🧠 2️⃣ درک عملی Orchestration

تو فهمیدی:

Workflow فقط یک فانکشن نیست.  
یک **state machine durable** هست که:

- Activity رو schedule می‌کنه
    
- منتظر نتیجه می‌مونه
    
- Fail رو مدیریت می‌کنه
    
- Retry انجام می‌ده
    
- Timeout رو enforce می‌کنه
    

Dashboard الان داره همین state machine رو نشون می‌ده.

---

## 🧠 3️⃣ فهمیدن Lifecycle اجرای Activity

الان در Dashboard می‌بینی:

- Activity Scheduled
    
- Activity Started
    
- Activity Running
    
- Pending Activities = 1
    

این یعنی:

Workflow منتظر Activity هست.

این دقیقاً همون چیزی هست که در سیستم‌های بزرگ اتفاق می‌افته.

---

# 🔎 چرا Workflow هنوز Running هست؟

چون Activity هنوز complete نشده.

یا:

- Worker برای Activity بالا نیست
    
- یا Activity timeout طولانی داره
    
- یا intentional delay گذاشتی
    

Dashboard دقیقاً این رو بهت نشون می‌ده.

---

# 🧩 چی باید از این تمرین یاد می‌گرفتی؟

### ✔ Workflow stateful هست

### ✔ Activity قابل retry هست

### ✔ Timeout تعریف میشه

### ✔ Worker باید register بشه

### ✔ Task Queue routing مهمه

### ✔ Event History منبع حقیقت هست

# 🚀 حالا یک رویه‌ی حرفه‌ای و کاربردی از این کار

حالا می‌خوای بدونی این رو در دنیای واقعی چطور استفاده می‌کنیم.

بذار یه سناریوی واقعی بگم:

---

# 🏦 مثال واقعی: سیستم ثبت سفارش

فرض کن کاربر سفارش ثبت می‌کنه.

Workflow:

```
CreateOrderWorkflow
```

Activityها:

1. ValidateUser
    
2. ReserveInventory
    
3. ChargePayment
    
4. SendEmail
    
5. CreateShipment
    

```

اگر Payment fail بشه:

- Retry می‌کنه
- اگر چند بار fail بشه → Compensation اجرا می‌کنه
- Inventory آزاد میشه

این یعنی:

**Distributed Transaction بدون 2PC**

---

# 📌 یک رویه حرفه‌ای که از این تمرین درمیاد

## 🔥 Pattern پیشنهادی Production

### 1️⃣ هر external call → Activity

- HTTP call
- DB write
- Kafka publish
- Email
- gRPC

---

### 2️⃣ داخل Workflow فقط orchestration

- شرط‌ها
- تصمیم‌ها
- ترتیب اجرا
- Parallel execution

---

### 3️⃣ برای هر Activity:

- Timeout مشخص
- Retry Policy مشخص
- Idempotent implementation

---

### 4️⃣ Monitoring با Dashboard

چک کن:

- Pending Activities
- Retries
- Timeout ها
- Workers count

---

# 🧠 Mental Model که باید بسازی

Temporal یعنی:

> Durable Function Execution Engine

تو داری کد Go می‌نویسی  
ولی در واقع داری یک **Distributed State Machine Durable** می‌سازی.

---

# 🔥 پیشنهاد مرحله بعد برای حرفه‌ای شدن

اگر می‌خوای اینو واقعاً کاربردی کنی، این مسیر رو برو:

---

## 🥇 مرحله 1 — Retry Policy اضافه کن

بذار Activity عمداً fail کنه  
ببین Dashboard چطور retry رو نشون میده.

---

## 🥈 مرحله 2 — Parallel Activities اجرا کن

دو Activity همزمان اجرا کن.

---

## 🥉 مرحله 3 — Compensation Pattern پیاده کن

اگر Activity دوم fail شد  
Activity اول رو rollback کن.

---

## 🏆 مرحله 4 — Child Workflow بساز

یک Workflow از داخل Workflow صدا بزن.
```
